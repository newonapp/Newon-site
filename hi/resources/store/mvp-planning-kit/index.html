OVERVIEW

An MVP is not a short feature list.

MVP is not “build less.”
It is choosing which hypothesis to test.

Problem → user → value → core flow →
priority → scope → validation criteria —
that order keeps version one from drifting.

This kit locks that sequence into worksheets
so the team agrees before build starts.

MODULES

A worksheet for
each decision in order.

01

PROBLEM DEFINITION

Write the problem users actually want solved
as a sentence — not a guess.
Blurry problems make blurry features.

02

TARGET USER

Clarify early users and the situations
where the product is used.
A product for everyone rarely ships as a first MVP.

03

VALUE PROPOSITION

State why someone should use this product
in one sentence.
Differentiation is a promise, not a feature count.

04

CORE USER FLOW

Design only the essential path
through the product.
Secondary screens wait.

05

FEATURE PRIORITIZATION

Rank work as Must / Should / Could
so cuts follow criteria, not mood.

06

MVP SCOPE

Decide explicitly what ships in v1
and what does not.
The exclusion list is a deliverable.

07

VALIDATION PLAN

Define hypotheses and signals
to observe before and after launch.
Separate “we built it” from “we learned.”

08

BUILD ROADMAP

Outline Prototype → MVP → V1
in one line of stages
so the current stage stays visible.

HOW TO USE

How to use it.

  1. 01

    Write the problem first

    Before any feature list,
    lock the user problem as one sentence on Problem Definition.

  2. 02

    Keep only early users

    On Target User, remove “later customers”
    and keep the people needed for the first test.

  3. 03

    Filter through value

    Anything that does not serve the Value Proposition
    or Core Flow leaves the Must column.

  4. 04

    Publish the exclusion list

    On MVP Scope, write what you are not doing now
    so stakeholders see the same boundary.

  5. 05

    Name validation signals

    List behaviors and feedback to watch on Validation Plan,
    then mark the current stage on Build Roadmap.
