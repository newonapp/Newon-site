개요

MVP는 작은 기능 목록이 아닙니다.

MVP는 ‘조금만 만들기’가 아니라
검증할 가설을 고르는 결정입니다.

문제 → 사용자 → 가치 제안 → 핵심 흐름 →
우선순위 → 범위 → 검증 기준까지
순서가 있어야 첫 버전이 흔들리지 않습니다.

이 키트는 그 순서를 워크시트로 고정해
만들기에 들어가기 전 합의를 만듭니다.

구성 모듈

결정의 순서를
워크시트로 만듭니다.

01

PROBLEM DEFINITION

사용자가 실제로 해결하고 싶은 문제를
추측이 아닌 문장으로 적습니다.
문제가 흐리면 기능도 흐립니다.

02

TARGET USER

초기 핵심 사용자와
사용이 일어나는 상황을 정리합니다.
모두를 위한 제품은 첫 MVP가 되기 어렵습니다.

03

VALUE PROPOSITION

왜 이 제품을 써야 하는지
한 문장으로 말합니다.
차별은 기능 수가 아니라 약속입니다.

04

CORE USER FLOW

사용자가 제품에서 거치는
핵심 경로만 설계합니다.
부가 화면은 나중에 둡니다.

05

FEATURE PRIORITIZATION

Must / Should / Could로 나눠
우선순위를 보이게 합니다.
감정 대신 기준으로 자릅니다.

06

MVP SCOPE

첫 버전에 넣을 것과
제외할 것을 명시적으로 결정합니다.
제외 목록도 산출물입니다.

07

VALIDATION PLAN

출시 전후에 확인할 가설과
관찰할 신호를 정합니다.
‘만들었다’와 ‘검증했다’를 구분합니다.

08

BUILD ROADMAP

Prototype → MVP → V1 단계를
한 줄로 이어 적습니다.
지금이 어느 단계인지 보이게 합니다.

결과

첫 버전의 경계가
분명해집니다.

01

SHARED PROBLEM

팀이 같은 문제를 가리키며
기능을 논의할 수 있습니다.

02

CUT TABLE

이번 MVP에 넣지 않는 항목이
문서에 남아 재논의가 줄어듭니다.

03

TESTABLE HYPOTHESIS

무엇을 검증하려는지가
구현 목표와 분리되어 적힙니다.

04

STAGE AWARENESS

지금이 Prototype인지 MVP인지
다음 단계로 넘어갈 조건이 보입니다.

사용 방법

이렇게 사용합니다.

  1. 01

    문제 문장부터 쓰기

    기능 목록을 적기 전에
    Problem Definition에 사용자가 겪는 문제를 한 문장으로 고정합니다.

  2. 02

    초기 사용자만 고르기

    Target User에서 ‘나중 고객’을 빼고
    첫 검증에 필요한 사람만 남깁니다.

  3. 03

    가치 제안으로 걸러내기

    Value Proposition과 Core Flow에 맞지 않는 기능은
    우선순위 표에서 Must 밖으로 보냅니다.

  4. 04

    제외 목록을 공개하기

    MVP Scope에 ‘이번에 안 함’을 명시해
    팀과 이해관계자가 같은 경계를 보게 합니다.

  5. 05

    검증 신호 정하기

    Validation Plan에 관찰할 행동·피드백을 적은 뒤
    Build Roadmap에서 현재 단계를 표시합니다.
