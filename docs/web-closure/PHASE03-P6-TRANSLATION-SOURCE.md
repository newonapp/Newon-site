# PHASE 03 P6 — Translation source: trace, candidates, and what is NOT decided

Status words: PASS / FAIL / NOT RUN / NOT VERIFIED. **No translation was approved, switched or applied.** Nothing in the build reads the candidate files.

## 1. `scripts/.translate-cache.json`: who reads it

| Script | In the build? | What it does with the cache |
|---|---|---|
| `apply-translate-cache.mjs` (step of `run-all-locale-patches.mjs`) | **yes** | fills a locale key **only when it is empty or still equals the English text**; an existing non-English value is never overwritten. Cache absent → `{}`: the step is a no-op, so the build stays deterministic. |
| `auto-translate-app-locales.mjs`, `fix-home-card-html.mjs`, `fill-news-history-i18n.mjs`, `fill-404-human-i18n.mjs` | no (manual tools, flag-gated or run by hand) | call machine-translation services over the network and **write** the cache / generated data. |

The cache is gitignored, so a clean checkout (CI) has none. A clean build therefore equals "tracked sources + English fallback".

## 2. Correction to the P5 statement "not derivable from any tracked source"

P5 said the committed non-English text exists only in generated HTML. That was **too strong**. Searching the committed (HEAD) tracked sources (`locales/`, `scripts/`, `templates/`) for each differing text (`translation-candidates.v1.json`, field `trackedSource`):

- Of the 11,988 HTML-hunk records, **9,349 have a comparable text (≥12 characters)**: **4,653 (50 %)** are also present in a tracked source (mostly `locales/_sp.<lang>.json`), **4,696 (50 %)** only in the committed page. 2,639 are too short or markup-only; the other 735 records are `json-key` records of `locales/_sp.<lang>.json`.

| Family | Files | In a tracked source | Committed page only | Too short |
|---|---|---|---|---|
| delete-account (12 apps × 7) | 84 | 684 | 174 | 334 |
| home flyout (`{lang}/index.html`) | 7 | 3,800 | 3,449 | 2,006 |
| portfolio | 91 | 169 | 1,073 | 299 |
| `locales/_sp.<lang>.json` | 7 | 735 `json-key` records (the tracked files themselves) | | |

- Why the build still writes English there: `apply-delete-account-locales.mjs` does `Object.assign(sp, deleteAccountFields("SubPing", lang === "ko" ? "ko" : "en"))`, i.e. **English for every non-Korean language, by design** (account-deletion pages for the stores). `apply-app-closing-copy.mjs` falls back to English the same way. So the German in `_sp.de.json` is overwritten in the working tree by a clean build (and would be lost if that output were committed).
- **Portfolio** pages: mostly committed-page-only text (169 of 1,242 comparable records are in a tracked source), so those can only be recovered from the candidate file or from git history.

## 4. Candidate data

`i18n-candidates/translation-candidates.v1.json` (+ `.tsv` for reviewers). Generated by `npm run extract:translation-candidates` on a tree after one clean build.

- **189 files**, **12,723 records** (27 files per language × 7 languages): de 1,830, es 1,782, fr 1,832, hi 1,825, id 1,853, ja 1,727, pt-br 1,874.
- Every record: `id`, `lang`, `page`, `kind` (`html-hunk` | `json-key`), `locator`, built text (what the build emits), committed text (what is committed), `trackedSource` (file at HEAD that also holds the committed text, or `null`), `origin`, `reviewStatus: "unreviewed"`. The source/approval fields are the facts available; **"approved" is never set**.
- **Lossless, tested:** re-applying the records to the built output reproduces the committed token stream in **189 of 189** files (0 structural failures). `npm run check:translation-candidates` re-derives the records from a built tree and **fails** if a drifted language file is not covered, if the committed or built text changed since extraction, or if reconstruction differs. Tamper tests: a changed built heading → FAIL; a newly drifting file → FAIL; clean tree → PASS.
- ko and en files are never extracted; nothing is overwritten with English or Korean.
